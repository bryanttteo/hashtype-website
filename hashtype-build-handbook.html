1. The job and the rules

HashType is a Singapore-based AI and automation solutions provider. It helps businesses run leaner by redesigning workflows around what AI makes possible. The focus is agentic automation, IoT, vision AI and bespoke business applications. It serves six industries: supply chain & logistics, manufacturing, offshore & marine, industrial services, real estate & construction, and retail, F&B & hospitality.

The site has two visitors to win over. One is an SME decision-maker, an owner or operations, plant or facilities manager, who should leave convinced HashType can cut cost, time or risk in their business. The other is a partner or evaluator, who should leave convinced HashType has delivered real work. The site succeeds when either one books a discovery call, demo or site survey.

What you will ship: a responsive five-page React site, live on Vercel and built from the GitHub repo. It must pass the Appendix B checklist on a phone and on a laptop.

Your materials and what each is for:

ItemRole
company-profile.mdSource of truth for offerings, industries and positioning; no claim may go beyond it
This handbookHow to deliver it, phase by phase
stitch-brief.md (Appendix D)Design brief you upload to Google Stitch in Phase 3
content/Approved copy, brand file, logo and images. Created in Phase 2, then used exactly as written.
Appendix CInputs still needed from you, and decisions still open

The rules:

  • Copy is locked once approved. The build uses content/ exactly as written. Nobody, including the AI, invents clients, numbers, certifications or features.
  • Stack: React with Vite, React Router for pages, and one global styles.css using CSS variables. No Tailwind, Bootstrap or component libraries. Add dependencies only when a rule below needs them.
  • Background is black (#000000) on every page and section. Surfaces may lift slightly (#0D1013), but never go light.
  • Every page is reachable from every other page through the navigation, and every URL works when typed in or refreshed directly.
  • The site must work at 375 px and at 1280 px wide.

  • Mint carries primary buttons (mint fill, black text), links and key highlights. It is very readable on black.
  • Indigo is too dark for body text on black (roughly 4:1 contrast). Use it only for gradients, borders, glows and large display type.
  • The logo's mint-to-indigo gradient can be the one signature element, for example a hero glow or a thin rule under section titles. Don't repeat it everywhere.

Type

Requested: Gothamono. Headings and UI labels use it. Body text uses a highly readable sans, or the same family if it has a comfortable text weight.

Four free candidates are compared in hashtype-font-options.html: A Montserrat + Inter (closest to Gotham), B JetBrains Mono + Inter, C Space Grotesk + IBM Plex Mono labels, D IBM Plex Mono + IBM Plex Sans. All are open-licence, so they can be self-hosted from public/fonts/. Record the choice in content/brand.md and in the build prompt.

Open item: I couldn't find a published font called "Gothamono". It may be Gotham (Hoefler & Co., a paid licence), a Gotham-style monospace, or a custom font you have. Before the build, we need the exact font name, the web font files (.woff2) and confirmation that the licence covers web use. If those aren't ready, the build falls back to a free stand-in: JetBrains Mono or IBM Plex Mono for headings, and Inter for body text. Swapping the font later means changing one line.

Placeholders for details not yet supplied

Contact details and the official enquiry email aren't ready, so the copy uses visible placeholders. They live in one file, content/contact-details.md (transcribed into src/content/site.js), and every page reads from it. Filling them in later is a one-file change.

Logo

An analogy for the content/build split: treat content/ as the script and React as the stage. Actors (components) speak the lines exactly as written. If a line needs to change, you edit the script, not the set.

3. The route — eighteen steps in six phases

Phase 1 — set up the project

  1. Clone bryanttteo/hashtype-website to your Mac.
  2. Scaffold a Vite + React app inside it, check it runs locally, and make the first commit.
  3. Create content/ and design/, and put the logo files in content/images/.

Phase 2 — write and approve the content

  1. Have Claude draft the five page files, brand.md and images.md from the company profile. Anything unconfirmed is marked [CONFIRM].
  2. Review every file, resolve every [CONFIRM], and lock the copy.

Phase 3 — design with Google Stitch

  1. Start a Stitch project, upload stitch-brief.md and paste the master prompt.
  2. Judge each screen with the five questions, and ask for one testable change at a time.
  3. Download the export: a zip with one folder per screen, plus DESIGN.md.

Phase 4 — arrange the design files

  1. Save DESIGN.md in the project root.
  2. Move the five screen images into design/ and rename them index.png, solutions.png, industries.png, customers.png and contact.png.
  3. Correct DESIGN.md so it matches Section 2: black background, tokens, font and button style.

Phase 5 — build

  1. Open Claude Code in the project folder, or upload the files to a chat app.
  2. Paste the build prompt. The AI writes the React components, pages, stylesheet and config.
  3. Run it locally, review against the prompt's rules, and quote any failed rule back for a single fix.

Phase 6 — ship and check

  1. Commit and push to the repo's main branch.
  2. Import the repo on Vercel (framework preset: Vite) and deploy.
  3. Run Appendix B on the live URL, on a phone and a laptop. Fix the worst failures and redeploy.
  4. Connect the domain, then submit sitemap.xml to Google Search Console.

5. Phase 2 — write and approve the content

New phase. The original pack came with finished copy; this project doesn't.

What you are trying to achieve: one file per page holding every word that will appear on it, in final form. The build then has nothing to invent. Paste this into Claude in the HashType Project, which already has company-profile.md:

Using company-profile.md and the page specification in Appendix A of the
HashType build handbook, draft the website copy as seven markdown files:
brand.md, home.md, solutions.md, industries.md, customers.md, contact.md,
and images/images.md (image manifest: filename, page, placement, alt text).

Rules:
- Lead with business outcomes (cost, time, risk, compliance), then the
  technology. Confident, practical, jargon-light, for SME decision-makers.
- Position HashType as AI-first: new workflows designed around AI, not
  digitised old processes.
- For each industry, match 1–3 relevant solutions; do not list everything.
- Mention EDG/PSG grant support where relevant.
- Do not invent clients, numbers, certifications, awards or capabilities
  that are not in the profile. Where a fact is needed but unknown
  (contact details, customer results, photos), write [CONFIRM: what is
  needed] instead of filling it in.
- Give every page a title (max 60 characters) and a meta description
  (max 155 characters) at the top of its file.
- Mark each heading, paragraph, list and button label clearly so it can
  be transcribed verbatim into React data files.

Then review each file. Read it out loud. If a sentence wouldn't survive a sceptical plant manager asking "prove it", cut it or back it up. Resolve every [CONFIRM]. Once no [CONFIRM] is left, the copy is locked. Commit it:

git add content
git commit -m "Lock v1 website copy"
git push

6. Phase 3 — design with Google Stitch

What you are trying to achieve: Stitch turns a written brief into screen designs, and its output is only as good as the real information in the brief. Save Appendix D as stitch-brief.md, upload it to Stitch, then paste:

Design a five-page website exactly as specified in the attached design
brief. Design all five screens — Home, Solutions & Services, Industries,
Customers, Contact — mobile first, with one shared style and the same
navigation on every page. The background is pure black (#000000) on
every screen and section; never use light or white sections. Use the
brief's colour tokens, fonts, page jobs and content precisely. Use the
mint colour for primary buttons with black text. Do not invent content,
client names, logos, statistics, pages or features that are not in the
brief.

If Stitch won't accept the upload, paste the whole brief below the prompt instead.

Then judge every screen with the five questions in Appendix B. Ask for one testable change at a time, for example "Make the primary button the only mint-filled element on the Home screen." When every screen passes, download the export.

Watch for black-background traps. Stitch often slips in a white "light section" for contrast, puts grey text on black that fails contrast, or draws the logo on a white card. Reject all three.

7. Phase 4 — arrange the design files

The export arrives as a zip with one folder per screen (each holding screen.png and code.html) plus DESIGN.md. Put DESIGN.md at the project root. Move the five screen.png files into design/ and rename each one after the page it becomes: index.png (Home), solutions.png, industries.png, customers.png and contact.png.

The home screen is called index because the home page of every site is served from the root (index.html). In React the same idea applies: Home is the / route.

Two warnings from experience still apply:

The screens lie about content. Stitch invents freely: fake client logos, made-up percentages, testimonials from nobody. For a B2B company this is a credibility risk, not just a mistake. Treat every screen as a layout reference only. The words come from content/ and nowhere else.

Don't ship Stitch's code.html. It loads a CSS framework from the internet and uses temporary image links. The build makes its own React components.

Before moving on, open DESIGN.md and correct it against Section 2. Check the black background, the exact hex tokens, the font family names, mint primary buttons with black text, indigo kept off body text, and one primary button per page. In the next phase this file becomes the AI's instruction sheet, and it follows the file, not what you meant.

If you are using a chat app (claude.ai, ChatGPT or Gemini), first upload DESIGN.md, content/brand.md, the five copy files and content/images/images.md. Then paste the same prompt with this line in place of its first paragraph:

I have uploaded DESIGN.md, the brand file, the five pages of copy and
the image manifest. Build the HashType website as a Vite + React
project and return every file with its full path (src/…, public/…,
vercel.json) so I can save each one into my repository.

A chat assistant never sees your images or fonts. It only writes references to them, which work because the files exist in your repository. Save each returned file at its exact path, and copy the images from content/images/ into public/images/, keeping file names exactly as they are.

Check it locally

npm run dev       # click through every page at 375 px and 1280 px
npm run build     # must finish with no errors
npm run preview   # test the production build, including refreshing /contact

In Chrome, open DevTools (⌥⌘I), turn on the device toolbar (⇧⌘M) and set the width to 375 to check the phone view.

Why the prompt is shaped this way. Keep these habits when you adapt it:

  • Name the sources and where they live. Exact paths remove the assistant's main excuse to guess.
  • Protect the copy, and separate it from code. "Exactly as written", plus data files instead of hard-coded text, keeps invented marketing lines out. Future copy edits also never risk breaking the layout.
  • State the checks up front. Each rule is one you can verify yourself, so you can quote it back when it fails.
  • Spell out the deploy details. The two classic React-on-Vercel failures are images that worked locally but break live (letter case in paths) and pages that 404 on refresh (missing rewrite). The prompt prevents both.

When the build misses, don't start over. Quote the rule that failed and ask for that fix only:

The menu does not close after I tap a link on mobile — the build rules
said the navigation closes after a link is tapped. Fix that and change
nothing else.
The Industries page contains text that is not in content/industries.md.
Replace src/content/industries.js with a verbatim transcription of that
file, unchanged, and change nothing else.
There is a light grey section on the Solutions page. The rule is a black
#000000 background on every section. Fix that and change nothing else.

10. If something goes wrong

  • Stitch keeps producing crowded layouts: the prompt is listing features instead of each page's one job. Point Stitch back at the job lines in the brief and regenerate.
  • Stitch adds white sections or fake logos: quote the brief's rule back ("pure black on every section", "no client names not in the brief") and ask for that change only.
  • Stitch won't export: take screenshots of the screens yourself, put them in design/, and ask Stitch to describe the design in writing. Save its answer as DESIGN.md.
  • The AI build ignores the design: check that DESIGN.md is at the root and the images are in design/, then point the assistant at them again by path.
  • The AI invented text: quote the protect-the-copy line and name the file, as in the second fix prompt above.
  • A page shows 404 when refreshed on the live site: vercel.json is missing or not at the repo root. It must contain a rewrite from /(.*) to /index.html.
  • Images or fonts work locally but not live: the path's letter case doesn't match the file name, or the file is in src/ instead of public/.
  • The Vercel build fails: run npm run build locally, since the error is the same. Fix it, push, and Vercel retries.
  • A blank white page live: open the browser console. It's usually a JavaScript error or a wrong asset path. Paste the exact error to the assistant.

Appendix A — the page specification

Five pages. Each page has one job, and everything on a page either serves that job or gets removed.

Global requirements (every page)

  • Header: logo/wordmark linking to Home, and nav with Home, Solutions, Industries, Customers and Contact. The current page is visibly indicated. A small outlined "Book a demo" link may sit in the header; it is secondary and never mint-filled.
  • Below 768 px the nav collapses into a toggle. All touch targets are at least 44 px tall.
  • Footer: logo, one-line description, nav links, email, phone, LinkedIn, UEN (if provided) and © HashType with the current year.
  • Black background throughout; one stylesheet; consistent type and colour per Section 2.
  • Every image has meaningful alt text from content/images/images.md.
  • No content beyond content/. No unverified claims, statistics, client names, certifications or awards.
  • Each page has its own title and meta description.

1. Home (/)

Who arrives: an SME decision-maker, often on a phone, from search, LinkedIn or a referral. They don't know HashType yet.

The one job: make them understand what HashType does for a business like theirs and book a discovery call.

Must contain: a hero with the logo, an AI-first positioning line and an outcome statement; three outcome pillars (for example cost, time, risk/compliance); a short teaser of the solutions linking to Solutions; an industries strip of six that links to Industries; a short grant-support note (EDG/PSG); and one primary call to action, "Book a discovery call", linking to Contact.

Must not contain: full service details, walls of technical jargon, more than one primary call to action, or any statistic without a source.

2. Solutions & Services (/solutions)

Who arrives: someone checking whether HashType can solve their specific problem.

The one job: let them match their problem to a solution in under a minute.

Must contain: the five solutions (Bespoke Business Applications, Digital Enablement, Intelligence via IoT, Vision AI, Agentic Automation), each as outcome first, then how it works. Also the business applications (AIM, CRM, Monitoring Platforms); the services (AI consultancy, process analysis, n8n automation, web design & SEO, grant applications, demo/site survey); and one primary call to action, "Book a demo".

Must not contain: pricing, vendor or tool logos you have no partnership for, or claims beyond the profile.

3. Industries (/industries)

Who arrives: someone who thinks "do they understand my industry?"

The one job: let them find their industry and recognise their own problems in it.

Must contain: the six industries, each with two or three typical problems and the one to three HashType solutions that fit (matched, not everything); jump links or tabs so a visitor can go straight to their industry; and one primary call to action, "Book a site survey".

Must not contain: invented case results or client names.

4. Customers (/customers)

Who arrives: someone nearly convinced, looking for proof that HashType has delivered.

The one job: build trust with real evidence.

Must contain: only customers cleared for public use. For each: name and logo, the problem, what was delivered, and the result (figures only if verified), plus a testimonial if one was given. Partners are credited where they co-delivered. One primary call to action: "Talk to us about your project".

Decision for v1: no customers are cleared, so this page launches as "Use cases" (route /use-cases, nav label "Use cases"). For v1, read "Customers" and /customers as "Use cases" and /use-cases everywhere in this handbook, including the build prompt, sitemap, design file names and Stitch brief. The rest of this section applies when the first customer is cleared.

Fallback: if no customer is cleared at launch, retitle the page "Use cases". Show industry scenarios with no client names, and add customers later without changing the layout.

Must not contain: logos used without permission, unverified numbers, or any suggestion that HashType delivered alone what partners co-delivered.

5. Contact / Book a demo (/contact)

Who arrives: someone ready to talk.

The one job: get them to request a discovery call, demo or site survey with no friction.

Must contain: the three request types as clear choices (each opens a pre-filled email in v1); email and phone; a short "what happens next" (for example "we reply within one business day", if you will commit to it); location (city or address, if provided); and LinkedIn.

Must not contain: long copy, or a form that collects personal data without a PDPA privacy notice.

Appendix B — the review checklist

Run this against the live Vercel URL: every page on a laptop, then every page on a phone (or a 375 px window). Fix the worst failures first and redeploy.

The five questions — every page

#QuestionPrinciplePass looks like
1What do I see in the first three seconds?Visual hierarchyThe most important element is unmistakably the most prominent
2What is this page for?One job per pageYou can answer in one sentence, and the primary action matches it
3Where does this surprise the user?Jakob's LawNav, links and buttons look and behave as on every other site
4What can be removed?Hick's LawNothing competes with the one job; exactly one mint-filled primary CTA
5Can a thumb hit this?Fitts's LawEvery link and button is comfortably tappable without zooming

Mobile checks — every page at 375 px

  • The nav collapses into a working toggle, all five pages are reachable from it, and it closes after a tap.
  • No horizontal scrolling anywhere.
  • Body text is readable without pinch-zooming.
  • Images and the logo scale down without overlapping text.
  • The page's one job is achievable within the first two screens of scrolling.

Brand checks

  • Every section is black; there are no white or light-grey bands.
  • The logo shows with no white box around it, and the favicon appears in the browser tab.
  • Body and muted text are clearly readable on black (contrast at least 4.5:1). Indigo is never used for body text.
  • Headings use the agreed font (or the documented fallback) on every page.

Content and claims checks

  • No [PLACEHOLDER] text remains anywhere on the live site (search the repo for [).
  • Every word on the site exists in content/: no lorem ipsum, no leftover AI commentary.
  • No client name, logo, statistic, certification or award appears that isn't cleared and verified.
  • Each industry shows one to three matched solutions, not the whole list.
  • Grant support (EDG/PSG) is mentioned where relevant, and every page ends with a demo, call or site survey CTA.
  • Each Contact request opens an email to the right address with the right subject line.

Technical checks (React and deploy)

  • npm run build completes with no errors, and the Vercel deploy is green.
  • Typing or refreshing /solutions, /industries, /customers and /contact on the live URL loads the page, and an unknown path shows the NotFound page.
  • The browser console shows no errors on any page.
  • The current page is indicated in the nav, and each route opens scrolled to the top.
  • Every image and font loads on the live site, with nothing linked from other websites.
  • Every image has meaningful alt text.
  • Each page has its own title and meta description (check the browser tab and view-source).
  • /robots.txt and /sitemap.xml load, and the sitemap lists all five routes on the live domain.
  • Sharing the URL in WhatsApp or LinkedIn shows the Open Graph image and description.

Self-score

Each page scores 0–5, one point per question passed, so the site scores out of 25. Any mobile-check or claims-check failure caps that page at 3. Be as hard on HashType's site as a prospective client would be, because they will be.
